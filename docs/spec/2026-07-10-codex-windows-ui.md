# Codex Desktop Windows 风格界面改造

## Background

Image Tools 已具备 Windows-first Tauri 桌面壳、FastAPI sidecar、会话与生成轮次历史、Provider 管理、参考图、图片参数和结果操作。现有前端也已经从终端式界面改为两栏工作台，但实际呈现仍然是通用表单应用：侧栏过宽且卡片化，主区空状态被放进居中卡片，Composer 常驻六列参数控件，文本按钮与边框过多，整体密度、留白和交互节奏都不像用户指定的 Codex Desktop Windows 版本。

本改造以用户提供的 Codex Desktop Windows 主界面截图为视觉基准。参考界面的核心特征是 Windows 原生标题栏、约占窗口 20% 的低对比侧栏、大面积无装饰主画布、任务流式内容，以及悬浮在底部的双层 Composer。

本 spec 是对 [`2026-07-09-desktop-image-workbench.md`](./2026-07-09-desktop-image-workbench.md) 中“Codex Desktop 风格”要求的细化，不改变图片创作工作台的产品定位、数据模型和核心生成能力。

## Problem Statement

当前 UI 虽然满足“两栏、会话、时间线、Composer”的结构要求，但视觉和交互仍存在以下问题：

- 界面由大量边框、卡片和常驻表单控件主导，缺少 Codex Desktop 的克制与留白。
- Composer 更像参数表单，不像任务输入区；Provider、模型、比例、尺寸、质量和张数同时占据主界面。
- 新建、重命名和删除会话依赖 `window.prompt` / `window.confirm`，破坏桌面应用沉浸感。
- 空白状态、运行状态、成功与失败记录没有形成统一的任务生命周期。
- 只有单一浅色视觉，没有跟随 Windows 系统主题的完整明暗主题。
- 文本按钮和临时符号过多，图标、菜单、弹窗和键盘交互缺乏统一规范。

## Goals

- 高相似度复刻用户指定的 Codex Desktop Windows 窗口结构、视觉层级、组件密度和交互节奏。
- 保留 `Image Tools` 名称、图标和图片创作语义，不复制 Codex 或 ChatGPT 品牌。
- 使用 Windows 原生标题栏，不在网页内容中绘制第二套窗口边框或标题栏。
- 将主界面改为低噪音侧栏、单列任务流和底部双层 Composer。
- 将参考图、Provider、模型和图片参数收进 Composer 的上下文行、摘要和弹出菜单。
- 新任务进入无持久化草稿状态，首次有效提交时自动创建会话。
- 将运行、成功和失败统一呈现在生成轮次任务流中。
- 同时实现浅色和深色主题，并跟随 Windows 系统主题切换。
- 保留现有会话历史、参数复用、结果图操作和 Provider 能力。
- 在 `1280x860` 默认窗口与 `960x640` 最小窗口下保持稳定布局、无重叠和无文字溢出。

## Non-Goals

- 不复制 Codex、ChatGPT、OpenAI 的名称、Logo、账号信息或产品文案。
- 不新增 Scheduled、Plugins、Sites 等 Codex/ChatGPT 功能。
- 不新增置顶、收藏、标签、独立图片库、素材中心或项目层级。
- 不引入终端、命令行或 slash-command 交互。
- 不引入 React、Vue、Svelte 或新的前端打包系统。
- 不重写 FastAPI 图片生成逻辑、SQLite schema 或 Tauri sidecar 架构。
- 不把浏览器入口提升为正式产品入口。
- 不在本轮增加云同步、账号、多用户、自动更新或系统凭据存储。

## Target Users

- 在 Windows 桌面上长期使用兼容 OpenAI 图片接口进行创作的个人用户。
- 熟悉 Codex Desktop Windows 交互，希望图片生成工具拥有同等桌面体验的用户。
- 需要围绕会话持续迭代图片、复用参考图、追溯参数和切换 Provider 的创作者。

## User Stories

- 作为用户，我打开应用后可以直接在 Codex 风格的空白任务页描述创作目标。
- 作为用户，我第一次提交提示词时不需要先填写会话名称，应用会自动创建会话。
- 作为用户，我可以从低噪音侧栏快速新建任务、管理 Provider、筛选并切换最近会话。
- 作为用户，我可以在同一任务流中看到提示词、运行状态、结果图和失败信息。
- 作为用户，我可以在不离开 Composer 的情况下切换参考图、Provider、模型和常用图片参数。
- 作为用户，我可以复制历史参数、把结果设为参考图或基于结果继续创作。
- 作为用户，我可以让界面自动跟随 Windows 浅色或深色主题。
- 作为键盘用户，我可以打开菜单、切换选项、关闭弹窗并提交任务，不依赖鼠标。

## Core Workflows

### 启动与新任务

1. 应用启动后显示新任务草稿页，而不是自动打开最近会话。
2. 左侧栏展示 `Image Tools Work` 品牌、搜索入口、`新建任务`、`Providers` 和最近会话。
3. 主画布显示简洁的创作提示和底部 Composer。
4. 此时不创建 SQLite 会话记录。

### 第一次提交

1. 用户输入提示词，并可选择参考图、Provider、模型和参数。
2. 前端先验证提示词与 Provider；缺少 Provider 时打开应用内 Provider 设置弹窗，不创建空会话。
3. 前端以提示词第一行生成会话标题；标题清理连续空白并限制为 36 个字符。
4. 前端调用现有会话 API 创建会话，再使用返回的 `session_id` 调用 `/api/generate`。
5. 侧栏选中新会话，主区立即插入乐观运行态。

### 后续生成

1. 用户在当前会话底部 Composer 输入下一轮调整。
2. 参考图、Provider、模型和参数摘要与本次提交绑定。
3. 提交后立即显示提示词和生成中状态。
4. 请求完成后重新读取会话生成轮次，用 SQLite 记录替换乐观状态。

### 成功与失败

1. 成功轮次展示状态、关键参数和结果图网格。
2. 结果图提供预览、下载、复制链接、设为参考图和基于结果继续等操作；次要操作进入省略号菜单。
3. 失败轮次保留在任务流中，展示简洁错误摘要以及重试、复制错误和详情操作。
4. 重试把原轮次参数恢复到 Composer，由用户确认后再次提交；不静默自动重试。

### 会话管理

1. 点击会话切换任务流，并恢复该会话未提交的本地草稿。
2. 侧栏搜索图标展开内联筛选框，不永久占据垂直空间。
3. 重命名和删除位于任务标题的省略号菜单。
4. 重命名使用应用内弹窗；删除使用带明确后果说明的应用内确认弹窗。

### Provider 管理

1. 侧栏 `Providers` 或 Composer Provider 菜单中的“编辑 Providers”打开设置弹窗。
2. 弹窗复用现有 Provider CRUD API，支持名称、Base URL、API Key 和默认模型。
3. API Key 默认脱敏；未填写新值时保留原 Key。
4. 保存后立即刷新 Composer 的 Provider / model 选择。

## Functional Requirements

### Windows 壳层与布局

- 保留 Tauri 原生 Windows 标题栏、最小化、最大化和关闭按钮。
- 网页内容必须贴合原生客户区，不再嵌套模拟窗口卡片。
- 默认窗口继续使用 `1280x860`，最小窗口继续使用 `960x640`。
- 侧栏宽度使用 `clamp(248px, 20.3vw, 280px)`，主区使用剩余宽度。
- 任务流内容最大阅读宽度为约 `760px`，在主区水平居中。
- Composer 最大宽度约 `746px`，最小窗口下保留至少 `24px` 水平边距。
- 固定格式组件必须有稳定尺寸，加载、悬停、状态变化和文字变化不得引发布局跳动。
- 窗口高度不足时仅任务流和侧栏列表滚动，Composer 保持可见。

### 视觉系统

- 字体优先使用 `Segoe UI Variable` / `Segoe UI`，并提供系统无衬线与 CJK 回退。
- 使用中性灰表面、细边框、克制阴影和小范围品牌蓝；不使用大面积渐变、装饰光球或单一蓝紫色主题。
- 普通控件圆角保持 `6px` 到 `8px`；双层 Composer 使用约 `20px` 圆角。
- 空白页不使用卡片容器，提示内容直接位于主画布。
- 不在页面区块外包浮动卡片；卡片仅用于图片结果、菜单和弹窗等确有边界的组件。
- 图标使用本地打包的 Lucide 图标。熟悉动作优先使用图标与 tooltip，不使用手绘 SVG 或文本符号代替。
- 图标按钮使用稳定方形尺寸，命令按钮才使用文字或图标加文字。

### 系统主题

- 默认跟随 `prefers-color-scheme`，由 Windows 系统主题驱动。
- 浅色与深色主题使用同一套空间、字号、边框宽度和交互结构，只替换颜色 token。
- 所有前景文字、边框、焦点环和危险状态需要满足可读性要求。
- Tauri/WebView 主题切换后不得要求重启应用。

### 侧栏

- 顶部品牌为 `Image Tools Work`，保留搜索图标。
- 一级入口仅包含 `新建任务` 和 `Providers`；不显示不可用的 Codex 功能入口。
- 会话以紧凑单行文本列表显示，默认不常驻缩略图卡片。
- 当前会话使用低对比背景突出，不使用粗边框或高饱和选中态。
- 底部展示本地工作区入口与设置图标，不模拟 ChatGPT 用户头像或账号。

### 任务流

- 一轮生成由用户提示词、运行状态、参数摘要、结果或错误组成。
- 用户提示词使用轻量右对齐消息表面；生成响应保持左对齐无大卡片容器。
- 结果图按数量使用稳定网格，最大四张；图片加载前使用固定比例占位，避免布局跳动。
- 图片操作默认在悬停、焦点或省略号菜单中显示，移动到操作区时不得遮挡主要内容。
- 完整参数放在详情折叠区，默认只显示 Provider/model、比例、尺寸、质量和张数摘要。
- 生成中使用无虚假百分比的进度状态；不展示后端无法提供的精确进度。

### Composer

- Composer 为悬浮双层结构，上层显示参考图与 Provider/model 上下文，下层包含可增长文本区与工具栏。
- 文本区自动增长到限定高度，超过后内部滚动；内容变化不得挤出窗口。
- `+` 菜单用于上传参考图或使用已有结果图。
- 参数按钮打开弹出菜单，包含比例、尺寸、质量和张数；输出格式、压缩、背景和审核放入高级参数子层。
- 工具栏默认只显示参数摘要，不常驻六列表单。
- 发送按钮使用圆形上箭头图标；提交中进入稳定 loading/disabled 状态。
- `Enter` 提交，`Shift+Enter` 换行；菜单与弹窗支持 `Escape` 关闭。

### 弹窗、菜单与可访问性

- Provider、重命名和删除使用应用内弹窗，不使用浏览器原生 prompt/confirm。
- 弹窗必须包含焦点圈定、初始焦点、`Escape` 关闭和关闭后焦点恢复。
- 菜单支持方向键、Enter/Space 选择、Escape 关闭，并正确维护 `aria-expanded`。
- 所有图标按钮都有可访问名称和 hover tooltip。
- 危险操作必须使用危险色和明确文案，不只依赖图标或颜色。

## Domain Terms

- **Codex Windows 视觉基准**：本次 UI 改造采用的窗口比例、侧栏层级、主画布留白、任务流和双层 Composer 设计语言；不包含 Codex 品牌或其特有业务功能。
- **新任务草稿**：尚未写入 SQLite 的临时创作状态；第一次有效提交后才成为会话。
- **参数摘要**：Composer 工具栏中对比例、尺寸、质量和张数的紧凑展示，不等同于完整参数编辑器。
- 其余术语继续采用 [`CONTEXT.md`](../../CONTEXT.md) 中的图片创作工作台、会话、生成轮次、Composer、Provider 和参考图定义。

## Implementation Decisions

- 保留 Tauri + FastAPI + 原生 HTML/CSS/JavaScript 技术栈，不引入新的前端框架或打包器。
- `frontend/workbench.js` 继续承载可由 Node 直接测试的纯状态逻辑，并新增草稿、自动标题、任务状态和参数菜单相关函数。
- `frontend/app.js` 负责 API 调用、事件编排和状态协调；DOM 渲染拆入独立 UI 模块，避免继续扩大单文件职责。
- `frontend/styles.css` 重建为颜色 token、Windows 壳层、侧栏、任务流、Composer、菜单、弹窗和响应式规则。
- Lucide 浏览器资源必须本地随应用打包，不依赖 CDN 或运行时网络。
- 会话草稿使用 `localStorage`，按 `draft:new` 或 `draft:session:<id>` 隔离；成功提交后清理对应草稿。
- 新任务第一次提交在前端串联现有 `POST /api/sessions` 与 `POST /api/generate`，不新增复合后端接口。
- 运行态先在前端乐观插入；请求结束后以 `GET /api/sessions/{id}/runs` 返回的数据库状态为准。
- 不修改 SQLite schema。现有 `generation_runs.status`、错误信息和参数快照继续作为历史来源。
- Provider 设置复用现有 CRUD API；本轮只新增完整桌面 UI。
- Windows 原生标题栏和窗口尺寸继续由 Tauri 管理；HTML 不模拟标题栏。

## Testing Decisions

- 所有行为变化先通过测试描述，再修改实现。
- Node 单元测试覆盖自动会话标题、草稿键、参数摘要、乐观状态转换和 Provider/model 切换。
- HTML 结构测试覆盖侧栏、任务流、Composer、菜单和弹窗，并确认不再存在常驻六列参数表单或不可用 Codex 入口。
- 现有 Python、数据库、生成流程、打包和 Tauri 配置测试必须继续通过。
- 增加 Playwright 视觉验证，覆盖 `1280x860`、`960x640`、浅色、深色、空白任务、活动任务、菜单、弹窗、运行、成功和失败状态。
- 视觉验证必须检查文字溢出、重叠、菜单越界、Composer 遮挡和图片占位布局跳动。
- Tauri 手动 smoke test 覆盖原生标题栏、系统主题实时切换、桌面热重载和窗口最小尺寸。
- Windows CI 继续验证 x64 安装包构建；发布前保存 Windows 实机截图作为最终视觉验收证据。

## Risks

- WebKitGTK 开发截图与 Windows WebView2 字体渲染存在差异；最终像素验收必须以 Windows 构建为准。
- `prefers-color-scheme` 在不同 WebView 版本上的更新时机可能不同，需要在 Tauri 运行态实测。
- 乐观运行态没有后端 run id，必须在请求结束后完整刷新生成轮次，避免重复记录。
- 首次提交需要串联创建会话与生成请求；若会话创建成功但生成前发生客户端异常，可能留下空会话，需要允许继续使用该会话。
- 原生 JavaScript 的菜单、焦点和弹窗状态容易互相干扰，必须保持模块边界并覆盖键盘测试。
- 高相似度复刻容易误加 Codex 特有功能；实现与评审必须坚持本 spec 的 Non-Goals。

## Open Questions

- 无阻塞问题。具体颜色值、间距和图标选择以用户已确认的可视化稿和 Windows 实机截图校准，不改变本 spec 的信息架构与行为。

# 桌面图片创作工作台

## Background

Image Tools 当前是一个本地图片生成工具：FastAPI 后端负责 OpenAI-compatible 图片接口代理、API Key 服务端保存、参考图上传、结果保存；前端提供提示词、参考图、尺寸、质量、张数、高级输出设置和结果预览；Tauri 桌面壳已经作为安装版方向存在。

这次改造参考 `cc-switch` 的 provider/config 管理思路，以及 Codex Desktop 的桌面工作台体验。但产品核心仍然是图片生成，不转向通用 AI 工具配置中心。

## Problem Statement

当前产品更像单次生成表单或终端式工具，缺少持续创作工作台所需的会话、历史、生成上下文和多 provider 管理。用户很难围绕一个创作主题持续迭代，也难以追溯某张图来自哪个提示词、参考图、模型和参数。

## Goals

- 将产品定位为 Windows 桌面优先的图片创作工作台。
- 用 Codex Desktop 风格的现代桌面应用界面替换旧的终端式布局。
- 保持核心能力为图片生成和参考图驱动的图片编辑。
- 提供两栏结构：左侧会话/历史列表，中间当前创作任务流。
- 在主区底部提供自然语言 Composer 输入区。
- 用本地 SQLite 保存会话和生成历史元数据，图片文件继续保存在本地目录。
- 支持多个图片 API provider 配置，并在 Composer 中快速切换 provider/model。
- 复用现有后端生成逻辑、参数能力、参考图上传、结果保存和 Tauri sidecar 架构。
- 第一版优先 Windows 桌面安装包。

## Non-Goals

- 不做通用 Claude/Codex/OpenAI 工具配置切换中心。
- 不把浏览器 Web 版作为正式用户入口。
- 不做终端模拟器、命令式 UI 或 `/settings`、`/options` 这类命令交互。
- 不做云同步、账号、多用户、多设备同步。
- 第一版不接 Windows Credential Manager，API Key 仍本地保存并在 UI 脱敏显示。
- 第一版不做系统托盘、全局快捷键、自动更新。
- 第一版不做标签、收藏、全文搜索、批量管理、导入导出、素材中心。
- 第一版不做内置图片编辑器、裁剪、涂抹、版本对比、批量导出。
- 不自动导入旧 `data/images/` 中的散落图片为历史会话。

## Target Users

- 在 Windows 桌面上使用兼容 OpenAI 图片接口进行创作的个人用户。
- 需要围绕一个主题持续生成、复用参考图、追溯参数和结果的图片创作者。
- 需要管理多个图片 API provider、Base URL、API Key 和模型的本地工具用户。

## User Stories

- 作为用户，我可以新建一个创作会话，用它承载一个主题或任务。
- 作为用户，我可以在左侧快速回到最近的会话和历史创作。
- 作为用户，我可以在一个会话里进行多轮图片生成，并查看每轮的提示词、参数、结果和状态。
- 作为用户，我可以把某张结果图设为参考图继续生成。
- 作为用户，我可以复制某一轮参数到 Composer，快速重新生成或微调。
- 作为用户，我可以配置多个图片 API provider，并在生成前切换 provider/model。
- 作为用户，我可以在桌面应用中完成主要操作，不需要通过浏览器打开本地端口。

## Core Workflows

### 首次启动与 Provider 设置

1. 用户打开 Windows 桌面应用。
2. 应用启动本地 sidecar 后端并打开桌面工作台窗口。
3. 如果存在旧版单一 `settings.json`，应用将其读取为默认 provider。
4. 用户通过设置弹窗新增、编辑或删除 provider。
5. API Key 默认脱敏显示；编辑时可以重新输入或替换。

### 新建与选择会话

1. 用户在左侧会话列表中新建会话。
2. 会话代表一个创作主题或任务，而不是一次 API 请求。
3. 会话列表展示标题、最近缩略图和更新时间。
4. 用户可以重命名或删除会话。

### 生成图片

1. 用户在中间主区底部 Composer 输入提示词。
2. 用户可通过按钮上传参考图。
3. 用户可通过快捷选择调整比例、尺寸、质量、张数、provider 和 model。
4. 高级参数通过按钮呼出弹窗或抽屉调整，不常驻右侧。
5. 提交后，时间线中创建一条生成请求记录。
6. 完成后，记录附带结果图网格；失败时保留失败记录和错误信息。

### 继续创作

1. 用户在任意结果图上预览大图、下载、复制本地链接。
2. 用户可以把结果图设为参考图继续生成。
3. 用户可以复制该轮参数到 Composer 后微调再生成。
4. 用户可以基于某一轮重新生成。

## Functional Requirements

- 应用主体验必须是 Tauri 桌面应用；本地 FastAPI 服务仅作为实现细节和开发测试入口。
- 第一版以 Windows 桌面安装包为优先发布目标。
- UI 必须是现代桌面工作台风格，不是终端式界面。
- 主布局必须为两栏：
  - 左侧：会话/历史列表。
  - 中间：当前会话的生成时间线与底部 Composer。
- 参数不设常驻右侧栏；通过 Composer 内快捷控件、菜单、弹窗或抽屉调整。
- 会话必须支持新建、重命名、删除。
- 每个会话必须支持多轮生成记录。
- 每轮生成记录必须保存提示词、参考图、参数、provider、model、结果图、错误信息、状态、创建时间。
- 时间线默认展示提示词摘要、结果图网格、状态/时间和关键参数 chips。
- 完整参数应折叠在详情中。
- 失败的生成也必须保留为时间线记录。
- 图片结果必须支持预览大图、下载、复制本地链接、设为参考图和复制参数到 Composer；不再提供与这两个操作重复的“基于结果继续”。
- Provider 设置必须支持名称、Base URL、API Key、默认模型。
- Composer 必须可以快速切换当前 provider/model。
- 新生成结果必须进入 SQLite 会话历史。
- 旧 `settings.json` 可读取为默认 provider。
- 旧 `data/images/` 不自动导入会话历史。

## Domain Terms

- **图片创作工作台**：桌面应用主体验，围绕会话、时间线、Composer 和图片结果持续创作。
- **会话**：一个创作主题或任务，例如“产品海报主视觉”。一个会话包含多轮生成记录。
- **生成轮次**：一次提交给图片 API 的生成请求及其状态、参数、结果或错误。
- **Composer**：主区底部的自然语言输入区，承载提示词、参考图、常用参数和生成动作。
- **Provider**：一个图片 API 供应商配置，包含名称、Base URL、API Key 和默认模型。
- **参考图**：用于图片编辑或继续生成的输入图片，可以来自上传或已有结果图。

## Implementation Decisions

- 前端可以重做信息架构和视觉，不要求保留旧终端式布局。
- 后端应尽量演进而不是推倒重写，复用已有图片生成、上传、保存和参数适配逻辑。
- 元数据使用本地 SQLite；图片文件继续保存在本地 `images/` 目录。
- 桌面版使用应用数据目录保存 SQLite、provider 设置、上传和生成图片。
- Web 浏览器入口不再作为正式产品体验，但可作为开发或测试入口保留。
- 继续使用兼容 OpenAI 图片 API 的接口路径和字段适配。
- Provider API Key 第一版本地保存，UI 默认脱敏；系统凭据存储推迟。

## Testing Decisions

- 后端需要覆盖 SQLite 数据模型、会话 CRUD、生成记录 CRUD、provider CRUD、旧设置迁移。
- 后端需要覆盖生成成功与失败都会写入历史记录。
- 前端需要覆盖 Composer 状态、参数复制、设为参考图、provider/model 切换、会话列表更新。
- 桌面验证需要覆盖 Tauri 启动 sidecar、读取应用数据目录、Windows x64 构建。
- 现有图片 API 参数适配测试应继续保留并扩展到 provider 场景。

## Risks

- 前端重做范围较大，容易和后端数据模型同时膨胀；需要拆小 ticket。
- SQLite schema 一旦落地，后续迁移需要纪律，建议从第一版就加入简单 migration 机制。
- Provider 与历史绑定不清会导致旧记录无法追溯当时使用的模型和参数。
- Windows sidecar 打包和路径处理容易出现平台特定问题。
- 如果保留 Web 开发入口，可能产生“桌面产品”和“浏览器入口”之间的体验分叉。

## Open Questions

- 第一版是否需要自动生成会话标题，还是只使用用户输入的标题和默认时间标题。
- 会话删除是否同时删除关联图片文件，还是只删除 SQLite 记录并保留文件。
- Provider 删除后，历史记录中 provider 名称如何展示：保留快照字段还是标记为已删除 provider。
- SQLite migration 工具使用轻量自建机制还是引入迁移库。
- Windows 构建验证是否需要在 CI 中成为必跑项。

## Suggested Ticket Entry Points

- 设计 SQLite schema 与数据访问层。
- 实现 provider 配置管理与旧 `settings.json` 迁移。
- 实现会话与生成记录 API。
- 改造生成流程，让成功和失败都写入会话历史。
- 重做桌面工作台两栏 UI。
- 实现 Composer、参数弹窗和 provider/model 快速切换。
- 实现时间线、结果图操作和继续生成流程。
- 更新 Tauri/Windows 桌面发布文档与验证流程。
